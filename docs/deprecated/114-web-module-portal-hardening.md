# 114 — The web module: what to take from the reference ERP, and what not to

**Status:** plan. Phases are executed and marked off in order.

Read against `zzref2/odoo14/addons/portal/`, `http_routing/`, `website/` and
`sale/controllers/portal.py` — the actual source, not from memory.

---

## 1. What the reference ERP's "web module" actually is

Three separate things wear that name, and only one of them is worth having here.

| the reference ERP addon | Is | For c-erp |
|---|---|---|
| `web` | the back-office UI framework (QWeb, actions, views) | **already solved** — c-erp has its own OWL SPA |
| `website` | a CMS: page builder, themes, snippets, ~40 companion addons | **no.** A locker-rental and electronics shop does not need a website builder, and it is the single largest surface in the reference ERP |
| `portal` | the *customer-facing document* framework: `/my/...`, access tokens, pagination, one authorization funnel | **yes — this is the part to take** |

So "web module" here means **the portal framework**, not a CMS.

## 2. What the reference ERP's portal does that c-erp does not

Reading `portal/controllers/portal.py` and `portal/models/portal_mixin.py`:

| # | the reference ERP mechanism | Why it matters | c-erp today |
|---|---|---|---|
| **A** | **`_document_check_access(model, id, token)`** — every portal document route funnels through one function: you either pass the ACL *or* present a valid per-record token | One place to get authorization right | **12 routes each repeat `WHERE id=$1 AND partner_id=$2`.** Correct today (journey 09-portal proves it) but it is 12 chances to drift |
| **B** | **`portal.mixin.access_token`** + `consteq` | Lets a customer open one document from an emailed link with no account, without weakening anything else | absent |
| **C** | **CSRF tokens** — HMAC(`database.secret`, sid+expiry), constant-time compared | The portal has 6 POST routes that change state | **absent.** `SameSite=Lax` is the only defence |
| **D** | **`pager()` + `_items_per_page`** | Lists are bounded and navigable | invoices `LIMIT 50`; orders and deliveries **unbounded** |
| **E** | **`/my/counters`** — portal home badges | One screen that says what needs attention | absent |
| **F** | searchbar sortings, as an **allow-list dict** | Sorting without letting the client name a column | absent |

## 3. Where a straight copy would be wrong

Adapting, not porting:

- **the reference ERP's portal is server-rendered QWeb; c-erp's is a JSON API + SPA.** So "portal home" is an endpoint returning counts, not a template. Pagination is query parameters, not a rendered pager widget.
- **the reference ERP emails share links. c-erp has no mail layer** (docs/112 names this as the largest gap). So a share link is **generated by staff and handed over deliberately** — exactly the pattern already established for admin-issued password resets in docs/111. Same shape, same reasoning, one house convention instead of two.
- **the reference ERP hangs `access_token` on each model** via a mixin. c-erp has no mixin machinery and would need to ALTER three tables. A **single `portal_access_token` table** keyed `(model, res_id)` is a better fit: it adds no columns, and it makes *"revoke every link we ever shared"* one statement instead of three, which is the operation you actually want in an incident.
- **`consteq` on tokens is not optional.** A token compared with `==` leaks its prefix through timing. c-erp already does constant-time comparison for passwords; tokens get the same treatment.
- **No public/anonymous ACL layer.** the reference ERP has a `public` user and record rules. c-erp's portal is scoped by `partner_id` on every query, which is simpler and stricter — keep it.

## 4. The phases

### W1 — One authorization funnel + share tokens  ✅ BUILT
The security core. Everything else depends on it.

- `portal_access_token (model, res_id, token, created_at, expires_at, revoked, created_uid)`,
  unique on `(model, res_id)` where not revoked.
- `portalCheckAccess(txn, model, resId, partnerId, token)` → `allow | deny`.
  Owner check first; token second; **constant-time compare**; expiry and
  revocation honoured. Every document route routes through it.
- Staff action `portal_share(model, res_id)` → a URL with the token, valid 30
  days, and `portal_revoke_share`.
- `GET /portal/doc/{model}/{id}?token=` — read-only HTML for one document, no
  session, no cookie.

**Security rules this phase must hold:** a token grants access to **exactly one
record** and never implies anything about its neighbours; an expired or revoked
token is worthless; a token for document A must not open document B; the
token-bearing route must not be able to write.

### W2 — CSRF  ⬜ NOT BUILT, AND DELIBERATELY SO

the reference ERP needs an HMAC CSRF token because its portal is **server-rendered HTML
forms**: a `<form method="post">` is a "simple request", so a cross-site page
can submit one, and the reference ERP supports session cookies that predate `SameSite`.

c-erp's portal is not that. Two properties already close the hole:

1. **The portal cookie is `SameSite=Lax` + `HttpOnly`.** A cross-site `POST`
   does not carry it, so the request arrives unauthenticated and every route
   answers 401 before doing anything. That is verified — journey 09-portal §8
   asserts a forged/absent cookie is refused on every route.
2. **Writes are scoped to the session's partner in SQL**, so even a request
   that somehow arrived authenticated could only act on its own records.

Adding an HMAC token dance on top would be ceremony: it would not close a hole
that is open, and it would add a token-refresh failure mode to every write.

**What would change this decision** — worth writing down, because it is the
kind of thing that silently stops being true:

- serving the portal over plain HTTP, or on a shared parent domain where a
  sibling subdomain is attacker-controlled (`SameSite` is same-*site*, not
  same-origin);
- adding a portal route that accepts an HTML form post rather than JSON;
- supporting a browser without `SameSite` enforcement.

If any of those becomes true, build W2 as originally specified.

### W3 — Pagination and the portal home  ✅ BUILT
- `page` / `limit` on orders and deliveries — both were **unbounded**, so a
  customer with years of history fetched all of it on every load, and so did
  anyone holding their password. Default 20, **hard ceiling 100 the caller
  cannot raise**.
- Totals ride in `X-Total-Count` / `X-Page` / `X-Page-Limit` headers rather than
  reshaping the body, so existing clients keep working.
- `GET /portal/api/home` → invoice / unpaid / order / quotation / delivery
  counts and the amount due. the reference ERP's `/my/counters`, one call instead of five.

*Sorting was not built.* Every list already has one correct order (newest
first) and no screen offers a sort control, so a `sort` parameter would be an
untested S-49 surface added for nobody. Add it with the allow-list when a UI
needs it.

### W4 — Statement of account  ✅ BUILT
- `GET /portal/api/statement[?date_from=&date_to=]`, `/print`, `/pdf`.
- Built from the **receivable ledger** (`account_move_line` on an
  `asset_receivable` account, posted moves only), not by adding invoices and
  subtracting payments. A statement assembled the second way is a *second
  opinion* about the balance, and second opinions drift; this one agrees with
  the trial balance by construction and picks up credit notes, write-offs and
  manual entries without a case being written for each.
- Opening balance, running balance, closing balance, **ageing** (current /
  1–30 / 31–60 / 61–90 / 90+) from `amount_residual`, so a part-paid invoice
  ages by what is left.
- Dates are validated as `YYYY-MM-DD` and refused otherwise rather than handed
  to PostgreSQL to interpret.

### W5 — Repeat order  ⬜ NOT BUILT
The last item from docs/113 §3b. Listed so the backlog is honest.

## 5. What is deliberately not built

A page builder, themes, snippets, `/shop`, product comparison, wishlists,
customer reviews, multi-language URL routing, a `public` user, and payment
acquirers. Each is a large surface, none is needed to run this business, and
every one of them widens the part of the system an anonymous visitor can reach.
